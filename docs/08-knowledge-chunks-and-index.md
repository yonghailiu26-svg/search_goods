# 第八课：知识整理与分块，让回答引用具体片段

**初读先看：[第八课白话版：跟着一条数据走完RAG](08a-rag-data-flow.md)。** 它用一个盒装问题，逐站展示原文、对象、索引JSON、检索结果、tool消息和最终响应之间的数据变化。本篇保留实现细节与验收，等你对上数据流以后再读。

日期：2026-10-18。本课只增加一个能力：**把规则文档预先整理成可检索、可追溯的片段。** 仍用关键词，不接Embedding或向量数据库。

当前默认检索已进入[第十二课重排](12-cross-encoder-reranking.md)，沿用第十课向量召回。第八课片段构建仍保留；需准备向量及重排模型，详见[总验收入口](00-course-map-and-acceptance.md)。复现本文关键词行为可设置KNOWLEDGE_RETRIEVAL=keyword。

## 1. 为什么要改，改在流程的哪个位置

第七课把一份Markdown的正文作为一条检索结果。资料很短时可以；文件变长后，问“一盒多少支”，可能把预算、售后等无关内容一起交给模型。上下文变大，而且只标文件名，不方便定位具体依据。

第八课把“整理资料”和“回答问题”分开：

```text
准备资料时，由我们执行一次命令，不调用模型：
knowledge/*.md → 按小标题、段落分块 → outputs/knowledge-index.json

用户聊天时：
用户问题 → 模型提出search_knowledge(query, limit)
        → Python检查索引版本，检索相关片段
        → 把片段正文和来源放入role=tool消息
        → 再次请求模型 → 回答并引用具体chunk_id
```

所以，**分块不发生在每一次模型请求里；检索发生在Agent执行知识工具时。** “离线准备”指在问答流程外准备，不是把DeepSeek改成本地模型。

在线检索仍会读取原文件来核对内容哈希，避免使用过期资料；但不会重新分块。这个小项目没有做缓存或增量索引。

可以类比前端：`knowledge/*.md`是源文件，构建命令生成可使用的数据产物，`search_knowledge`是运行时读取产物的入口。这里的JSON保存的是片段列表和元信息，没有向量。

## 3. 用实际包装规则看分块结果

现在三份规则生成五个片段，默认每片最多260个Python字符：

| chunk_id | 小标题section | 原文行号 | 正文字符数 |
| --- | --- | --- | --- |
| KB-PACK-001-C001 | 盒支换算依据 | 4～9 | 118 |
| KB-PACK-001-C002 | 缺少盒装数量时怎么回答 | 11～14 | 101 |
| KB-PACK-001-C003 | 按支销售与预算计算 | 16～20 | 141 |
| KB-PRICE-001-C001 | 无二级标题 | 4～9 | 186 |
| KB-FILTER-001-C001 | 无二级标题 | 4～9 | 209 |

第一片段包含文档的练习声明和第一小节，所以从第4行开始。没有二级标题的短文档仍保留为一块，不为了分块而强行切碎。

例如用户问：“具体SKU没有提供盒装数量时，应如何答复？”

```text
检索结果之一：KB-PACK-001-C002
小标题：缺少盒装数量时怎么回答
原文：knowledge/KB-PACK-001.md，第11～14行

用户问某商品一盒多少支时，应先确定SKU，再查商品详情里的包装说明。
如果具体SKU没有提供盒装数量，应明确回答“未提供，无法确定”……
```

模型依据返回的正文回答，并标记 `[KB-PACK-001-C002]`。这里的具体答案来自正文；ID和行号只是帮助追溯。

关键词检索可能同时返回几个相关片段，不保证只返回最合适的一条；`limit`是返回条数上限，不是每片的字符长度。

## 4. 分块函数具体做了什么

建议阅读顺序：`build_index → chunk_document → paragraph_spans`。

### 4.1 先读取固定规则目录

`read_sources`只处理`knowledge`目录下`KB-*.md`，文件格式沿用第七课：

```markdown
# 文档标题
关键词：包装、盒装、换算

## 一个小标题

这一节的规则正文。
```

程序将换行归一化为`\n`用于切片和行号计算，同时用原文件字节计算SHA-256，保存为`source_version`。它不读取用户在问题里指定的任意路径。

### 4.2 按小标题划分主题

`chunk_document`找出`## `开头的二级标题及位置。不同小节分别打包，避免只因为总长度没超过260，就把两个主题合并。

没有二级标题时，全文正文作为一个主题。首个标题前的说明与第一节一起处理。这是本课约定的简化Markdown格式，不是支持所有Markdown结构的通用解析器。

### 4.3 优先保留段落，再处理过长内容

`paragraph_spans`返回的是正文中的位置，例如`(start, end)`，内容通过`text[start:end]`取出：含start位置，不含end位置。

拆分优先级：

1. 先按空行找到段落。
2. 单段过长时，按`。！？；`尝试拆成句子。
3. 连一个句子都超过上限时，才按字符长度切开。
4. 同一主题中相邻段落或句子能放进上限时，再打包在同一片段。

判断能否合并的核心是：

```python
if pending is not None and end - pending[0] > max_chars:
    spans.append(pending)
    pending = None
```

`pending[0]`是当前待打包片段的起点；`end`是准备加入内容的终点。两者之差包括中间的空行。若合并后超长，就先保存旧片段，再开始下一片。

默认260只是为了观察分块效果，**字符数不等于Token数**。本课没有重叠区，也没有通用分词器。最后的硬切仍可能拆开语义，因此真实长文要抽样检查，不能只看构建成功。

### 4.4 关键词也要跟着片段收窄

假设一份文档作者标了`包装、预算`。不能把这两个词都无条件给每个片段，否则查询“预算”时，纯包装片段也会命中。

本课只保留“文档声明过，且出现在本片小标题或正文中”的关键词：

```python
local_keywords = sorted({
    word for word in keywords
    if word.casefold() in keyword_text
})
```

`casefold()`统一字母大小写；中文不受影响。`{...}`去重，`sorted`让结果顺序稳定。

在线检索仍按命中的关键词数量排序，同分按chunk_id排序；零命中不返回。它不会理解所有同义表达，例如资料关键词是“预算”，用户只说“钱够不够”，可能没有命中。分块解决资料组织问题，不会自动解决语义召回问题。

## 5. 检索结果的字段各代表什么

一条结果结构如下，正文为展示而截短，实际会返回完整片段：

```json
{
  "source_id": "KB-PACK-001",
  "chunk_id": "KB-PACK-001-C002",
  "title": "包装与盒支换算规则",
  "section": "缺少盒装数量时怎么回答",
  "source": "knowledge/KB-PACK-001.md",
  "source_version": "原文件SHA-256的完整64位值",
  "start_line": 11,
  "end_line": 14,
  "content": "## 缺少盒装数量时怎么回答\n\n用户问某商品一盒多少支时……",
  "score": 1,
  "matched_keywords": ["盒装"]
}
```

| 字段 | 用途 |
| --- | --- |
| source_id | 哪一份文档 |
| chunk_id | 该文档中的哪一个片段，模型用它引用 |
| source | 项目内原文路径 |
| start_line/end_line | 原文行号，1开始，包含首尾；同一行硬切的多个片段可能行号相同 |
| source_version | 原文件字节内容的哈希，识别是否改过；不是业务生效日期或权威认证 |
| content | 真正供模型使用的证据正文 |
| score | 本课关键词命中数量，不是答案正确率或事实置信度 |

`chunk_id`按文档内次序编号。同样的资料和配置重建时编号一致；在前面增加内容或调整切块参数后，编号可能改变，所以排查旧回答时还要一起看`source_version`。

最终`/chat`响应中，完整正文在`tool_trace[].passages`；`sources`提供来源摘要和`citation_id`，便于调用方展示出处。`citation_id`当前等于chunk_id；旧测试资料没有chunk_id时兼容source_id。

## 6. 为什么修改资料后必须重建

构建产物除了chunks，还保存文档清单、每份文件的哈希、分块参数和分块算法版本。

在线`load_index`会对照当前资料：

```text
当前源文件路径 + 哈希
       对比
索引中保存的路径 + 哈希
```

修改、增加、删除资料，或分块算法版本不一致，会拒绝使用旧索引。缺失、格式损坏、重复片段ID等也会报错，不能冒充“没有相关规则”。

`/chat`会停止并提示检查资料、运行构建命令；直接运行`load_index`可区分过期或损坏提示。这里继续使用已有`tool_failed`错误路径，没有把底层异常原文或文件内容输出到HTTP错误中。

构建时先完整生成数据，再写临时文件，最后替换旧JSON。解析失败不会先清空旧索引。不过原文已变更时，旧索引仍会被判定过期，必须修复资料后重建，不能靠保留旧文件绕过校验。

## 7. 你本地怎么操作

在项目根目录执行：

```powershell
# 第一次使用第八课，或修改knowledge中的规则后执行；不调用模型/数据库
.\.venv\Scripts\python.exe build_knowledge_index.py

# 启动现有聊天页；已经开着--reload时等代码重载即可
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

打开`http://127.0.0.1:8000/`，建议开新会话试这两个问题：

```text
为什么不能把所有签字笔默认每盒12支？请查本地规则，引用具体片段。

具体SKU没有提供盒装数量时，应如何答复？请查本地规则。
```

观察回答中的`-C001/-C002`引用；通过`/docs`或浏览器Network查看`sources`及`tool_trace`中的行号和版本。若8000在本机不可绑定，可以把启动端口和访问地址一起换成8001。

想观察尺寸变化，可使用：

```powershell
.\.venv\Scripts\python.exe build_knowledge_index.py --max-chars 120
# 观察索引后恢复本课默认值
.\.venv\Scripts\python.exe build_knowledge_index.py
```

上限允许80～2000字符。调整参数要重新运行构建命令；编辑源文件后，重启服务不能代替重建。
